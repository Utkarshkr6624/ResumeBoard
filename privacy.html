Privacy

There is nowhere for your resume to go.

Resumeboard is a set of static files with no backend behind them. There is no account system, no database, and no operator reading what you type. What follows is not a policy written to be reassuring. Every claim names the file it comes from, and you can open that file and read the line.

The short version

  • No cookies. The codebase never writes to document.cookie, for preferences, sessions, or anything else.
  • No analytics, no telemetry, no page-view counters, no error-reporting service, no advertising, and no pixels.
  • No account, no sign-in, and no email address collected.
  • No server. The files your browser downloads are the whole application.
  • Your resume is written to storage inside your own browser and is never transmitted.
  • Exactly one feature is designed to reach another host: PDF import, which downloads a reader from cdnjs.cloudflare.com after you choose it, and shows you both addresses before it starts.

The in-app privacy dialog in the topbar overflow menu says the same three things in three sentences. If the two ever disagree, the source files on this page are the ones that decide which of them is right.

What is stored, and where

When you type, the app saves your resume locally so it is still there when you come back. That save happens in your browser's own storage, keyed to the address you opened the app from. It is written by your browser, readable by your browser, and removable by your browser. The persistence layer is assets/js/core/idb.js, and the code that decides what goes in is assets/js/core/store.js.

IndexedDB: the normal case

IndexedDB is the browser's built-in structured storage. It holds real JavaScript objects rather than text, which is why a full resume, including a photo encoded as a data URL, fits without stuffing a large JSON string into a single key. The app uses exactly one database, with these contents:

  • resumeboard — the database name, at version 1, with a single object store called kv.
  • resume:current — the resume you are editing, as one JSON object.
  • resume:undo — an array of the last 40 states before the current one, so undo survives a closed tab. The app keeps up to 100 in memory during a session and writes the newest 40 to disk.

Those are the literal strings in the source, so you can check them yourself. Open developer tools, go to Application in Chrome and Edge or Storage in Firefox and Safari, find the resumeboard database, and open the kv store. If it is empty, nothing has been saved yet and nothing is being stored.

localStorage: the fallback, and four small preferences

Some browsers refuse IndexedDB in private windows, in locked-down configurations, or when a profile is out of room. When that happens the app falls back to localStorage and prefixes every key it writes with rb:. The fallback exists because a resume you cannot save is worse than a resume stored the wrong way, and because losing the whole document to a storage API that threw would be a silent failure.

The trade-off is size. localStorage holds a few megabytes for the entire origin, so a resume with a large photo can hit that ceiling. If the write fails, the app keeps the resume in memory for the life of the tab and tells you so when you press Save now in the command bar. Your work is not lost while the tab is open, and it is not on disk either.

These are all the localStorage keys the app writes, in every mode:

KeyWhat it holds
rb:resume:currentYour resume, but only in the localStorage fallback. In the normal case this key does not exist.
rb:resume:undoThe same undo history, in the fallback only.
rb:themeWhether you chose light or dark, as the word light or dark. The guides and the button at the top of this page use it too.
resumeboard:themeThe same light or dark choice, written by the topbar switch inside the builder.
rb:onboarding.v1A single 1, set once you have dismissed the first-run dialog. Delete it and the dialog comes back.
rb:commands:recentsThe few commands you have run recently, so the command bar can suggest them. Command text only; it is never sent anywhere.
resumeboard.rail.collapsedWhether the section rail is collapsed.

None of these is a cookie. localStorage is readable only by scripts on this origin, is never attached to a request, and is not sent to a server under any circumstance. The app uses no sessionStorage at all.

What is inside the stored resume

One object, and it is the same object the JSON export writes out. It holds your name, contact details, summary, every section and entry, your design choices, and a few internal fields: a generated id, creation and update timestamps, the template you are using, and the language tag the app read from your browser.

A photo, if you add one, is stored as a data: URL inside that object, so the image is part of the local record and is covered by everything on this page. It is not uploaded anywhere and it is not cached by the service worker.

The app reads your browser's own locale to pick a date format, a page size, and whether a photo is expected in your region. That comes from Intl in the browser. It never asks a server where you are, and there is no IP-derived region anywhere in the codebase.

The network

The builder has no beacon, no sendBeacon, no XMLHttpRequest, no WebSocket, and no first-party endpoint of any kind. Type is set in a system font stack, so there is no web font to download and no third-party font server in your history. The only image loading in the export path refuses to run unless the source is a data: URL, so a photo can never become a request to someone else's server.

The requests the app does make

  • Your browser fetches the app's own files: the HTML, the stylesheets, and the scripts. That is the application, and it is the same for everyone.
  • Nothing else. The editor lives on its own page, #start, and the marketing front door on index.html. Both are ordinary static files served like any other page, so the page you are reading describes every request the app makes.
  • PDF import, described next.

There is no advertising network, no data broker, no retargeting pixel, no analytics product, no session replay, no A/B testing tool, and no hosted font or icon font on any page of this site.

The one exception: PDF import

Reading a PDF needs a real PDF engine, and this project ships none. So when you choose Import, then PDF, then pick a file, the app injects a <script> tag pointing at a pinned version of pdf.js on cdnjs. The import panel shows you both addresses before anything is fetched, and offers a cancel that works for as long as the download is in flight.

These are the exact URLs, taken from the constants at the top of assets/js/ui/importer.js:

https://cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174/pdf.min.js https://cdnjs.cloudflare.com/ajax/libs/pdf.js/3.11.174/pdf.worker.min.js

The version is pinned rather than tracked, so the file you receive today is the file anyone receives today. The script tag is added with crossorigin="anonymous" and referrerpolicy="no-referrer", which means the request carries no cookies and no information about the page you came from. The worker is the second address: it is fetched by the browser when the parser starts working, and it is the only reason there are two URLs.

After it loads, the library runs inside your browser and is given the bytes of the file you picked. Your PDF is not uploaded. Nothing about the file, its size, its name, or the text inside it is sent to cdnjs or to anyone else. cdnjs sees one request for two public JavaScript files, in the same way it sees a request from any other site. If you never use the PDF option, the request is never made.

The other three import routes — a .docx file, a .json file, and pasted text — are unpacked and parsed locally and make no request at all.

Share links: the one way your resume can travel

The builder can produce a link that contains your entire resume. It is written into the part of the address after the #, and browsers never send a URL fragment in a request. There is no server to log it, no referrer header to leak it, and no analytics script to see it. The resume is decoded from the link by assets/js/share.js, in your browser, and the fragment is then cleared from the address bar.

Two honest caveats. Anyone who has the link can read the resume, so treat it like a document you handed to someone. And the encoding is not encryption: it is deflate plus base64, which is a compression format, not a cipher.

A photo is left out of the link by default, because a base64 image runs to hundreds of kilobytes and a URL that long stops working in some browsers. It is only included if you explicitly ask, and only when it is under 60,000 characters. The reader refuses any payload over one megabyte.

What the service worker caches

sw.js does two things and nothing else. It makes the app's own static files load from a cache when the network is slow or absent, and it lets a deploy be picked up immediately. The worker only registers when the app is served over http or https; opened from a folder on disk there is no service worker, and the app runs the same way without one.

What is precached

Both front doors are precached in full: the marketing page on index.html and the editor on #start. The list lives at the top of sw.js and holds both documents, every stylesheet and script either one loads, the manifest, and the install icons: 58 paths. With no network at all the editor still opens and still edits, which is the point of the list being that long.

Anything outside that list, such as the writing guides or the example pages, is cached the first time you request it rather than up front. A missing precache entry therefore cannot fail the install, and if one ever does go missing the worker names it in the developer console instead of leaving you to discover it somewhere with no signal.

What it deliberately does not cache

  • Your resume. It is never in an HTTP response, so it can never be in a cache. The worker only ever sees requests the browser makes for files, and your document travels through IndexedDB instead.
  • Anything on another origin. The fetch listener returns immediately when the request URL is not on this site's origin, which is why the lazy pdf.js is never stored by the worker. The browser's own HTTP cache may still hold it, as it would for any script on any page; the app does not manage that.
  • Any fetch or XHR. A fetch() has an empty destination, so it falls outside the list of things the worker will answer and goes straight to the network.
  • Range requests and anything marked no-store.
  • Old versions. The cache name is a hash of the worker's own source combined with the revision stamp written beside it, so a change to the worker or to the list inside it names a new cache, and on activation every older cache is deleted. A deploy that changes a cached file without changing the worker is covered by the stamp, which has to be bumped by hand: a browser only reinstalls a worker whose bytes differ, so without it a corrected stylesheet would keep being served out of the cache. Activation is when the new worker takes over, which is after you accept the offered reload, so until then the old cache is still there and nothing is lost if you never accept.

Navigations are the exception to cache-first: a page request goes to the network first, so you get the current version, and falls back to this browser's own copy of that exact page only if the network fails. It never substitutes one page for another, so opening a page offline that you have never opened before says so plainly rather than quietly handing you the landing page instead. A hard reload skips the cache entirely, so holding Shift while you reload always reaches the network and can never be talked into by a stale copy.

How to delete everything

Deleting is not a request you make to us, because there is no us to make it to. You remove the storage directly and it is gone. Export a backup first if you want to keep it.

From inside the app

The overflow menu in the topbar has Start a new resume. It replaces the stored resume with an empty one, which is the right tool for a shared machine. One caveat, stated plainly: the reset is an ordinary edit, so the resume you had is pushed onto the undo stack rather than destroyed, and the app writes that stack to storage. In other words, Start a new resume empties your document, it does not erase it. The previous version stays readable in resume:undo until the stack rolls over, and the console approach below removes it properly.

From the browser

  • Open developer tools with F12, or by right-clicking and choosing Inspect.
  • Go to Application in Chrome and Edge, or Storage in Firefox and Safari.
  • Under Indexed Databases, delete the database named resumeboard.
  • Under Local Storage, remove every key listed in the table above.
  • Under Cache Storage, delete the caches whose names start with rb-static-. These hold the app's files, not your data; deleting them only means the next visit downloads the app again.
  • Or use the browser's own controls. In Chrome and Edge, Settings → Privacy and security → Third-party cookies → See all site data and permissions, then search for the site's address and delete it. In Safari, Settings → Privacy and security → Manage Website Data, then search for the site.

If you opened the app from a folder on disk

Pages opened from file:// sit on a storage origin of their own and browsers handle that inconsistently. The reliable method is the console. Open the app, press F12, choose the Console, and run:

indexedDB.deleteDatabase('resumeboard') Object.keys(localStorage).filter(k => k.startsWith('rb:')).forEach(k => localStorage.removeItem(k))

Then reload the page. You will get an empty resume, which is the correct result. That is what deleting means.

Things that delete it without asking

  • Clearing browsing data, or site data, in your browser settings.
  • Using a private or incognito window. Anything stored there is discarded when the window closes.
  • Browser eviction under storage pressure. Browsers may reclaim site data when a device is low on space, and there is no notice and no copy kept anywhere else.
  • Opening the app in a different browser, a different profile, or at a different address. Each of those is a separate storage bucket, so each starts empty.
  • Uninstalling the browser, wiping the profile, or changing the folder the files live in.

That is the cost of a local-only app, without hedging: a deletion is complete, because there is no copy on any server, and an accident is not recoverable by anyone.

How to export a backup

A backup is a single JSON file containing the same object the app saves locally, including your design settings. It is plain text you can read in any editor, and it is small enough to email to yourself.

  • Open the builder and use the export button in the topbar, choosing the JSON format. The file is named after your name — alex-morgan.json if your name is Alex Morgan, or resume.json if you have not set one.
  • The file is built in the page as a blob and handed to your browser's own download mechanism. It is not posted anywhere, and there is no upload step to wait for.
  • Keep it somewhere you control: a folder, a cloud drive you chose, an email to yourself. The app has no opinion and keeps no copy.
  • To restore, open the builder on any device and use Import to load the file. It restores your content and your design settings, and it does not restore the undo history.

The example resumes can be downloaded the same way, so you can read the exact shape of the file before writing your own. Start with the software engineer example or the product designer example; both have a Download JSON button.

The exported file is a snapshot. It does not update itself and it is not synced. If you keep editing, export again.

Eviction, and what the app does to reduce it

The resume is written about 400 milliseconds after you stop typing, not on every keystroke, and the app writes once more when the tab is closed or navigated away from, so the last edit before you leave is not the one that gets lost. It also asks the browser, once at start-up, to mark this site's storage as persistent, which is the standard request that stops a browser reclaiming an origin's data when a device runs low on space.

All of that is a local write. There is no automatic export file, no second copy in a folder you did not choose, and no mirror on a server. If the browser evicts the data anyway — and a browser is free to, because the request can be refused — the only version that survives is the one you exported. The example resumes are a good place to see what a finished file looks like before you trust the process with your own.

If you are on a shared computer

The storage belongs to a browser profile at an address, not to you. Anyone who opens the builder in that same profile sees the resume you left there, including your email, phone number, and address. This is the most common way a local-only app leaks, and it has nothing to do with us.

  • Export the JSON first. Do this before anything else, because after a reset the file is the only copy.
  • Use a private or incognito window for anything you would not leave on screen. Nothing in it survives the window closing.
  • When you are done, use Start a new resume in the overflow menu, and if the machine is not yours, delete the database as well. The reset is an ordinary edit: the previous resume moves into the stored undo history, which is written to disk like everything else.
  • Do not leave a share link in the address bar. The link is a complete copy of the resume, and it is readable by anyone who has the string.

Third parties

One, and only on a path you choose. Resumeboard has no advertising network, no data broker, no analytics vendor, no session-replay tool, no customer support platform, no error-reporting service, and no subprocessor, because there is no processor and no data to process. cdnjs, the content delivery network that serves pdf.js, is the single external host the codebase can reach, and it is reached only when you ask for PDF import.

Everything this site serves is a file in the same directory tree, from favicon.svg to sw.js. There is no build step, no bundler, no package downloaded at runtime, and no web font.

Children, and changes to this page

The builder is not directed at children, and it collects nothing from anyone, so there is no personal information held about a child. If you are under 16, ask a parent before putting personal details into a resume you plan to share.

This page is a plain file in the same tree as the application, which is also why it can be checked. Every claim above names the source file it comes from, and the app is plain HTML, CSS, and JavaScript that you can read in full. If a claim here and a line of code ever disagree, the code is the truth and the claim is the bug.

Questions people ask

Is my resume uploaded anywhere?

No. The builder writes your resume into your own browser, in a database called resumeboard, and it never opens a connection that carries it. The one feature that is designed to reach the network is PDF import, which downloads a PDF reader from cdnjs.cloudflare.com after you ask for it and shows you the two exact addresses first. The file you pick is read in your browser and is not uploaded.

Can the browser delete my resume without asking me?

Yes, and this is the one real cost of a local-only app. Browsers may reclaim site data when a device is low on space, clearing your browsing data removes it, and a private window throws it away when it closes. At start-up the app asks the browser to mark its storage as persistent, which lowers the risk but does not remove it. If you want a copy that no browser can take from you, export the JSON file and keep it somewhere you control.

What happens if I use a shared or work computer?

The resume is tied to that browser profile and that address, so the next person to open the builder on the same profile sees what you typed. Do the export first, then use Start a new resume in the overflow menu, and if the machine is not yours delete the database as well, because that reset is an ordinary edit and the previous resume moves into the stored undo history. A private window is the cleaner option, because everything in it is discarded on close.

Does a share link send my resume to a server?

No. A share link puts the whole resume in the part of the address after the #, which browsers never put in a request. The resume is decoded from the link in your browser. What is true is that anyone holding the link can read the resume, so treat it like a document you handed over. Your photo is left out of links unless you deliberately ask to include it, and only if it is under 60,000 characters.

Where do I send a privacy question?

Nowhere, because there is no server to receive it. This page is a plain file served from the same directory as the app, and every claim on it names the source file it comes from, so the fastest answer to a question is usually to read the line it points at. If you would rather read about the design decisions behind all of this, the about page covers the trade-offs, and the guides cover the writing.
