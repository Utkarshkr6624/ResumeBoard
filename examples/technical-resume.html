Why this works

Eight decisions, each visible in the document on the left.

  1. The summary is a sentence your reader can repeat. "I take a customer's failed install and turn it into a configuration, a timeline, and a number they can sign off" is a line a hiring manager can say to their boss in the corridor. "Passionate systems engineer with a knack for complex problems" is not a sentence anyone can repeat.
  2. Scale is stated, because a technical reader cannot infer it. 400 customers, 22 networks, 60 sites, 40 engineers trained. "Managed a large customer base" tells an engineer nothing they can use, and the number next to it tells them everything.
  3. Products are named the way the vendor names them. Ardent Gateway, Modbus TCP, journald. Keyword filters and recruiter searches are literal, and "monitoring solutions" is not a product anyone searches for.
  4. The bullets are about faults, not features. Sixty tickets a quarter down to eleven is a technical claim with a method behind it. "Improved system performance" is unfalsifiable, and anyone who has done the work reads it as noise.
  5. It acknowledges that there are two readers. The rota line is uptime language for an engineer; the pre-sales line is scoping language for a commercial reader. Both earn their place, because the reader of your resume is not only the person who forwards it to you.
  6. Projects stay in. Technical hiring managers read them, and they are the part of the page that proves the skills block is not aspirational. Each one names the constraint — four commands by hand, a case the vendor tool misses — rather than listing a stack.
  7. Confidentiality is handled with altitude, not a disclaimer. "A vendor gateway fleet", "a district firewall replacement" say the scale without naming a customer. Nobody needs the customer name; everybody needs to know whether it was three sites or three hundred.
  8. Credentials carry their renewal date. A certification that lapsed is a liability rather than an asset, so the year the reviewer sees is the year it is next due. Where a credential has no renewal, the issue date is the fact that matters.

Adapting it

  1. Reorder for the reader, not for the chronology of the field. Support, infrastructure, and pre-sales weight the same three years very differently, and the summary is the only part of the page you should rewrite per application without touching anything else.
  2. Moving from support into development means rewriting verbs, not adding experience. "Resolved" becomes "built", "documented" becomes "designed" — but only where that is true. A resume that claims to have shipped something you only supported is found out in the first technical screen.
  3. Delete any tool you would be uncomfortable being asked to pair on. On a technical resume a tool listing is a claim of interview readiness, and the pairing session is where the claim gets tested. A shorter, honest list beats a longer one you have to defend.

If the same work has to survive a two-column layout as well as a parser, the writing guides set out when that is safe, and how ATS read resumes covers what the parsers actually do.

Questions this situation raises

  1. How technical should a technical resume get? It depends entirely on who reads it. For an engineering manager, name versions and protocols and assume the reader knows what they imply. For a recruiter, a protocol list is a filter that quietly removes you. The version that survives both readers is a plain-language summary over a precise skills section, so the same page serves a first screen and a first conversation.
  2. Can I put unpaid projects on a technical resume? Yes, and they often carry more weight than another job title, because they are inspectable. Describe the problem, what you built, and one fact somebody else could check, with a link to the repository if there is one. Do not present a weekend project in the language of a shipped system.
  3. Should I include a home lab? Only if you can talk about it for ten minutes without overselling it. It is genuine evidence of hands-on time and it is also the easiest line on the page to be challenged on, so state it as what it is: where you learned the routing and VLAN work listed above. One honest line, not a photograph and not an inventory.
